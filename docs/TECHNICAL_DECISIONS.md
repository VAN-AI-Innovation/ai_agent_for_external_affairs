# 기술 의사결정 기록

이 문서는 대외업무 통합 AI 에이전트를 개발하면서 내린 주요 기술 선택과 그 이유를 기록합니다.

포트폴리오에서는 단순히 “무엇을 만들었는지”보다 “왜 그렇게 만들었는지”, “다른 선택지는 무엇이었는지”, “문제를 어떻게 판단했는지”가 중요하므로 개발 과정에서 계속 업데이트합니다.

## 2026-08-14: Day 1 초기 환경 구성

### 작업 범위

- 프로젝트 디렉터리 구조 구성
- Python 실행 환경 및 의존성 설정
- OpenAI LLM API 연동 구조 구성
- `.env`, `.env.example`, `.gitignore` 기반 환경변수 관리
- 기본 API와 Agent 실행 구조 구성
- React 기반 테스트 UI 구성
- README 기본 작성

현재 단계에서는 계약서 검토, 기관 리서치, 미팅 준비, 컨택 문안 작성 등의 실제 고도화 기능을 구현한 것이 아니라, 앞으로 기능을 붙일 수 있는 실행 가능한 골격을 만드는 것이 목표였습니다.

## 1. 왜 FastAPI를 선택했는가

### 고려한 선택지

- FastAPI
- Flask
- Django

### 선택

백엔드는 FastAPI를 사용했습니다.

### 이유

FastAPI는 API 서버를 빠르게 만들 수 있고, Pydantic 기반 요청/응답 검증을 기본적으로 사용할 수 있습니다. 이 프로젝트는 초기부터 프론트엔드와 백엔드를 분리하고, 나중에 계약서 검토, 리서치, 회의록 정리 같은 여러 API가 늘어날 가능성이 높습니다. 따라서 라우터, 스키마, 의존성 주입 구조가 잘 맞는 FastAPI가 적합하다고 판단했습니다.

Flask도 가볍고 빠르게 시작할 수 있지만, 요청/응답 스키마 검증이나 API 문서화는 별도 구성이 더 필요합니다. Django는 관리자 기능, ORM, 인증 등에는 강하지만 Day 1 범위에서는 구조가 다소 무겁다고 판단했습니다.

### 남은 검증 포인트

- API가 많아질 때 라우터 분리 구조가 유지보수에 충분한지 확인
- 인증, 파일 업로드, 작업 이력 저장이 들어갈 때 현재 구조를 확장할지 별도 서비스 계층을 둘지 판단

## 2. 왜 React를 선택했는가

### 고려한 선택지

- React
- Streamlit
- Next.js
- 백엔드 API만 먼저 구현

### 선택

프론트엔드는 React + Vite로 구성했습니다.

### 이유

이 프로젝트는 단순 챗봇보다 더 복잡한 업무 도구로 커질 가능성이 큽니다. 예를 들어 계약서 업로드, 리스크 항목 테이블, 참석자 리서치 카드, 컨택 문안 편집, 회의록 후속 업무 체크리스트 같은 UI가 필요해질 수 있습니다. 이런 인터랙션이 늘어날 경우 React가 상태 관리와 컴포넌트 분리에 유리합니다.

Streamlit은 빠른 프로토타입에는 좋지만, 실제 서비스형 UI로 확장할 때 디자인과 인터랙션 제어가 제한될 수 있습니다. Next.js는 라우팅과 서버 렌더링까지 필요할 때 좋지만, Day 1에서는 백엔드가 이미 FastAPI로 분리되어 있으므로 Vite 기반 React가 더 단순했습니다.

### 남은 검증 포인트

- 기능이 많아질 때 React Router 도입 여부
- API 상태 관리가 복잡해질 경우 TanStack Query 도입 여부
- 결과물을 문서처럼 편집해야 할 경우 rich text editor 도입 여부

## 3. 왜 LLM provider를 분리했는가

### 고려한 선택지

- API 라우터에서 OpenAI SDK를 바로 호출
- Agent 클래스에서 OpenAI SDK를 바로 호출
- `LLMProvider` 추상화를 두고 OpenAI 구현체를 분리

### 선택

`backend/app/llm/base.py`에 `LLMProvider` 인터페이스를 두고, `backend/app/llm/openai_provider.py`에 OpenAI 구현체를 분리했습니다.

### 이유

초기 구현은 단일 모델 기준이지만, 시중 LLM API를 사용한다는 조건이 있고 나중에 모델을 교체하거나 비교할 가능성이 있습니다. API 라우터나 Agent 코드 안에 OpenAI SDK 호출을 직접 넣으면 모델 교체 시 수정 범위가 커집니다.

Provider를 분리하면 Agent는 “텍스트를 생성한다”는 역할만 알고, 실제 모델 호출 방식은 숨길 수 있습니다. 이후 Anthropic, Gemini, Azure OpenAI, 사내 프록시 API 등으로 바꾸더라도 `LLMProvider` 구현체만 추가하면 됩니다.

### 남은 검증 포인트

- 스트리밍 응답을 도입할 경우 provider 인터페이스 확장 필요
- JSON 스키마 출력이 필요해질 경우 `generate_json` 같은 별도 메서드가 필요한지 검토
- 모델별 토큰 비용과 지연시간을 기록할 로깅 구조 필요

## 4. 왜 Agent 모듈을 별도로 만들었는가

### 고려한 선택지

- API 라우터 안에 프롬프트 작성 로직 포함
- 기능별 함수를 하나의 파일에 작성
- Agent 클래스로 업무 로직을 분리

### 선택

`ExternalAffairsAgent` 클래스를 만들고, 업무 유형별 힌트를 `CAPABILITY_GUIDE`로 분리했습니다.

### 이유

최종 목표는 대외업무 전반을 지원하는 에이전트입니다. 계약서 검토, 사전 리서치, 미팅 준비, 컨택 문안, 회의록 정리는 입력 데이터와 출력 형식이 서로 다릅니다. 따라서 API 라우터는 HTTP 요청 처리만 담당하고, 실제 업무 로직은 Agent 모듈이 담당하도록 나누었습니다.

현재는 하나의 Agent 안에 capability를 나누는 수준이지만, 기능이 커지면 `ContractReviewAgent`, `MeetingPrepAgent`, `OutreachAgent`처럼 분리할 수 있습니다.

### 남은 검증 포인트

- 기능별 Agent를 언제 분리할지 기준 필요
- 프롬프트 버전 관리 방식 필요
- 업무 결과 품질 평가 기준 필요

## 5. 왜 `.env.example`만 Git에 포함했는가

### 선택

`.env`와 `.env.*`는 `.gitignore`에 추가하고, 예시 값만 `.env.example`에 남겼습니다.

### 이유

API Key는 GitHub에 올라가면 안 되는 민감정보입니다. 실제 키는 로컬 `.env`에만 저장하고, 협업자나 평가자는 `.env.example`을 보고 어떤 환경변수가 필요한지 알 수 있게 했습니다.

### 확인한 내용

- `.gitignore`에 `.env` 포함
- `.env.example`에는 실제 키 없이 placeholder만 포함

## 6. 왜 프론트엔드와 백엔드를 각각 실행 단위로 분리했는가

### 고려한 선택지

- 백엔드와 프론트엔드를 각각 수동 실행
- 루트 명령어 하나로만 실행
- 각각 실행도 가능하고, 루트에서 동시 실행도 가능한 구조

### 선택

백엔드와 프론트엔드를 각각 실행할 수 있도록 `dev:backend`, `dev:frontend` 명령을 만들고, 루트에서는 `npm run dev` 한 줄로 두 서버를 동시에 실행하도록 구성했습니다.

### 이유

이 프로젝트는 React 프론트엔드와 FastAPI 백엔드가 역할이 다릅니다. 프론트엔드는 사용자 입력과 결과 표시를 담당하고, 백엔드는 API 요청 처리, Agent 실행, LLM API 호출을 담당합니다. 두 서버를 분리해두면 한쪽 문제가 생겼을 때 원인을 좁히기 쉽습니다.

동시에 개발할 때는 매번 터미널을 두 개 열어 각각 명령어를 입력하는 것이 번거롭습니다. 그래서 루트 명령어 `npm run dev`를 추가해 한 번에 실행할 수 있게 했습니다. 내부적으로는 `concurrently`를 사용해 백엔드와 프론트엔드를 별도 프로세스로 유지하면서 로그에는 `backend`, `frontend` 라벨이 붙도록 했습니다.

### 비교 결과

수동 실행 방식은 구조 이해에는 좋지만 반복 실행이 번거롭습니다. 반대로 하나의 명령만 있으면 편하지만, 백엔드만 따로 테스트하거나 프론트엔드만 재실행할 때 불편합니다. 그래서 두 방식을 모두 지원하는 구조가 Day 1 개발 환경에는 가장 적합하다고 판단했습니다.

### 남은 검증 포인트

- Docker Compose를 도입할 필요가 있는 시점 판단
- 운영 배포 시 프론트 정적 빌드와 백엔드 API를 어떻게 분리할지 결정
- 개발 서버 로그가 많아질 경우 로그 파일 저장 방식 검토

## 7. Day 1에서 일부러 하지 않은 것

### 실제 계약서 분석 고도화

아직 PDF/DOCX 파싱, 조항 분류, 리스크 룰셋은 구현하지 않았습니다. Day 1 범위가 초기 환경 구성이고, 문서 처리 기능은 별도 이슈로 분리하는 편이 안전합니다.

### 웹 리서치 자동화

상대 기관과 참석자 사전 리서치는 추후 검색 API 또는 브라우징 도구 연동이 필요합니다. 현재는 LLM에 사용자가 제공한 맥락을 바탕으로 정리하도록만 구성했습니다.

### DB 저장

요청 이력, 회의록, 담당자, 후속 업무를 저장하려면 DB가 필요하지만 Day 1에서는 제외했습니다. 다음 단계에서 SQLite 또는 PostgreSQL을 비교할 수 있습니다.

### 인증

개인/회사 업무 데이터를 다룰 가능성이 있어 인증은 필요하지만, 로컬 프로토타입 단계에서는 제외했습니다.
