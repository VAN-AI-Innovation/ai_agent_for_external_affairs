# 대외업무 통합 AI 에이전트

계약서 검토부터 사전 미팅 준비, 1차 컨택, 미팅 후속 정리까지 대외업무 전반을 지원하는 AI 에이전트 프로젝트입니다.

## 현재까지 구현한 내용

- FastAPI 기반 백엔드 API
- React + Vite 기반 프론트엔드
- PDF/TXT/MD/DOCX/이미지 계약서 입력과 텍스트 추출
- 계약서 핵심 조항, 의무사항, 위험 요소, 확인 필요 사항 구조화
- 긴 계약서 처리를 위한 chunk 분할과 로컬 RAG 검색
- 로컬 경량 NLP 분석 엔진과 Qwen 로컬 생성 모델 연동
- 기관 리서치, 미팅 준비, 협력 평가, 1차 컨택, 후속 정리 업무 지원
- 우측 하단 플로팅 챗봇, 퀵 버튼, 대화 히스토리, 간단 매뉴얼 검색
- 결과 복사, 좋아요/싫어요 피드백, 최근 실행 기록
- 로컬 AI 출력 품질 보정을 위한 프롬프트 강화, 후처리, 재시도 로직
- `.env` 기반 환경변수 관리
- 백엔드와 프론트엔드를 각각 독립 실행하거나 한 번에 실행할 수 있는 개발 스크립트

기술 선택 이유와 비교 내용은 [기술 의사결정 기록](docs/TECHNICAL_DECISIONS.md)에 정리합니다.
주차별 작업 과정은 [주차별 개발 기록](docs/WEEKLY_PROGRESS.md)에 정리합니다.
Push 단위 작업 요약은 [Push 기록](docs/PUSH_LOG.md)에 정리합니다.

## 구조 설계 메모

초기 개발에서는 백엔드와 프론트엔드를 분리해 각각 독립적인 서버로 실행하도록 구성했습니다. 백엔드는 API 요청 처리, Agent 실행, 계약서 파일 텍스트 추출, 로컬 분석 엔진 실행을 담당하고, 프론트엔드는 사용자가 업무 유형을 선택하고 요청 결과를 확인하는 화면을 담당합니다. 이렇게 역할을 나누면 문제가 발생했을 때 API 문제인지 UI 문제인지 구분하기 쉽고, 추후 계약서 검토, 미팅 준비, 컨택 문안 작성 같은 기능을 각각 확장하기도 수월합니다.

다만 개발할 때마다 터미널을 두 개 열어 백엔드와 프론트엔드를 따로 실행하는 것은 번거롭기 때문에, 루트에서 `npm run dev` 한 번으로 두 서버가 함께 실행되도록 했습니다. 즉, 내부 구조는 분리해 유지보수성을 확보하고, 실행 경험은 단순하게 만들어 개발 효율을 높이는 방향으로 구성했습니다.

계약서 분석은 외부 API 없이 동작하도록 로컬 경량 NLP 방식으로 구현했습니다. GitHub에서 널리 쓰이는 TextRank/TF-IDF 계열의 추출 요약 아이디어를 참고해, 문장 중요도 계산, 계약 조항 키워드 매칭, 위험 규칙 탐지를 조합했습니다. 기관 리서치, 미팅 준비, 협력 평가, 1차 컨택, 후속 정리 기능은 Hugging Face의 `Qwen/Qwen2.5-0.5B-Instruct` 로컬 생성 모델을 사용하도록 구성했습니다.

## 기술적으로 고민한 지점

이 프로젝트는 단순한 템플릿 응답에서 끝나지 않고, 실제 대외업무 흐름을 여러 기능으로 확장하는 것을 전제로 설계했습니다. 현재 구현에서는 아래 기준을 두고 구조를 잡았습니다.

- **역할 분리**: API 라우터는 HTTP 요청과 응답만 담당하고, 업무 로직은 Agent 모듈로 분리했습니다. 이후 계약서 검토, 미팅 준비, 컨택 문안 작성처럼 서로 다른 업무 흐름이 추가되어도 라우터가 비대해지는 것을 줄이기 위한 선택입니다.
- **무과금 로컬 분석**: 계약서 분석은 TF-IDF/TextRank식 문장 점수화와 계약 리스크 키워드 규칙을 사용했습니다. 업로드된 계약서 원문을 근거로 일관된 분석 결과를 만들 수 있습니다.
- **로컬 생성 모델 사용**: 계약서 외 업무 유형에는 `Qwen/Qwen2.5-0.5B-Instruct`를 사용합니다. 0.5B급 instruction 모델이라 비교적 가볍고, API 결제 없이 로컬에서 실행할 수 있습니다.
- **보안 기본값**: 계약서 원문과 대외업무 요청을 외부 API로 보내지 않고 서버 내부에서 처리합니다. API Key 의존성을 제거해 면접 시연과 로컬 개발이 안정적입니다.
- **개발 편의성과 디버깅 균형**: 프론트엔드와 백엔드는 각각 독립 실행할 수 있게 두면서도, 루트에서는 `npm run dev` 한 줄로 동시에 켤 수 있게 했습니다. 독립 실행은 문제 원인 추적에 유리하고, 동시 실행은 반복 개발 속도를 높입니다.
- **실패 상황 처리**: PDF가 아니거나, 비어 있거나, 텍스트를 추출할 수 없는 스캔 PDF일 때 사용자에게 명확한 오류 메시지를 반환하도록 했습니다.
- **기록 기반 개발**: 기술 선택 이유와 비교 내용은 `docs/TECHNICAL_DECISIONS.md`, 주차별 작업 과정은 `docs/WEEKLY_PROGRESS.md`에 따로 기록했습니다. 기능을 추가할 때마다 “왜 이렇게 구현했는지”를 남겨 포트폴리오에서 개발 과정과 판단 근거가 보이도록 하기 위한 목적입니다.

## 계약서 파일 핵심 조항 및 위험 요소 분석

PDF, TXT, MD, DOCX, PNG, JPG/JPEG 형태로 제공되는 계약서를 입력하면 계약 내용을 텍스트로 추출하고, 긴 문서를 처리 가능한 단위로 나눈 뒤 RAG 검색으로 관련 조항을 찾습니다. 이후 로컬 경량 분석 엔진이 문장 중요도, 계약 조항 키워드, 위험 규칙을 조합해 핵심 조항, 주요 의무사항, 위험 요소, 추가 확인이 필요한 내용을 구조화해 정리합니다.

이 기능은 대외업무 담당자가 계약서를 처음 검토할 때 놓치기 쉬운 조항을 빠르게 파악하고, 단순 요약과 실제 리스크 검토를 구분해 볼 수 있도록 만드는 것을 목표로 합니다. 면접이나 포트폴리오 관점에서는 단순 챗봇이 아니라 “문서 입력 → 전처리 → AI 분석 → 구조화된 업무 결과”로 이어지는 실무형 AI 워크플로우를 구현했다는 점을 보여줄 수 있습니다.

### 처리 흐름

```text
계약서 파일 업로드
→ 파일 형식별 텍스트 추출
→ 긴 계약서 텍스트 분할
→ 항목별 관련 조항 검색(RAG)
→ 계약 내용 분석
→ 구조화된 결과 생성
```

### 주요 작업 내용

- **계약서 파일 입력 기능**: 사용자가 PDF, TXT, MD, DOCX, PNG, JPG/JPEG 계약서를 업로드할 수 있도록 입력 흐름을 추가합니다.
- **파일 형식별 텍스트 추출**: PDF는 `pypdf`, DOCX는 `python-docx`, TXT/MD는 인코딩 판별, PNG/JPEG는 OCR을 사용해 텍스트를 추출합니다.
- **긴 계약서 분할 처리**: 계약서를 의미 단위 또는 길이 기준으로 chunk 분할해 긴 문서에서도 안정적으로 검색하고 분석합니다.
- **RAG 기반 관련 조항 검색**: 계약 개요, 핵심 조항, 의무사항, 위험 요소, 확인 필요 사항별 검색 질의를 사용해 관련성이 높은 원문 chunk를 찾아 분석 근거로 활용합니다.
- **핵심 조항 추출**: 계약 목적, 계약 기간, 금액, 해지, 비밀유지, 손해배상, 관할, 지식재산권 등 주요 조항을 항목별로 정리합니다.
- **위험 요소 분석**: 일방에게 불리한 조항, 책임 범위가 과도한 조항, 모호한 표현, 누락된 보호 조항 등을 단순 요약과 별도로 분리해 표시합니다.
- **확인 필요 사항 생성**: 법무 검토, 상대방 확인, 내부 의사결정이 필요한 질문 목록을 생성합니다.
- **분석 결과 구조화**: 프론트엔드에서 바로 표시하기 쉽도록 계약 개요, 핵심 조항, 주요 의무사항, 위험 요소, 확인 필요 사항으로 나누어 반환합니다.

### 출력 항목

- **계약 개요**: 계약 당사자, 계약 목적, 기간, 금액 등 전체 맥락을 요약합니다.
- **핵심 조항**: 계약서에서 의사결정에 중요한 조항을 항목별로 정리합니다.
- **주요 의무사항**: 각 당사자가 수행해야 하는 업무, 지급, 보고, 제공 의무 등을 구분합니다.
- **위험 요소**: 불리하거나 모호하거나 추가 협상이 필요한 조항을 별도로 분석합니다.
- **확인 필요 사항**: 계약 체결 전 확인해야 할 질문과 체크리스트를 생성합니다.

### MVP 범위

MVP에서는 일반적인 텍스트 기반 PDF와 텍스트 문서, DOCX 문서, PNG/JPEG 이미지 계약서를 지원합니다. 이미지 계약서는 OCR을 사용하므로 문서 품질, 이미지 해상도, 글자 선명도에 따라 인식률이 달라질 수 있습니다. 스캔 PDF 자체의 페이지별 OCR은 추후 고도화 기능으로 분리합니다.

완료 기준은 다음과 같습니다.

- PDF, TXT, MD, DOCX, PNG, JPG/JPEG 계약서를 입력할 수 있을 것
- 계약서 주요 내용을 항목별로 확인할 수 있을 것
- 단순 요약과 위험 요소 분석이 구분되어 출력될 것
- 긴 계약서도 분할 처리되어 모델 입력 한도 문제를 줄일 것
- RAG 검색으로 항목별 관련 원문 조각을 분석에 활용할 것

### 현재 한계와 개선 방향

현재 이미지 계약서 처리는 VLM(Vision-Language Model)이 아니라 OCR 기반 텍스트 추출 방식으로 구현했습니다. 즉, 이미지 안의 글자를 먼저 텍스트로 뽑아낸 뒤 계약서 분석 파이프라인에 전달하는 구조입니다. 이 방식은 별도 유료 API 없이 로컬에서 동작하고 MVP 범위에 적합하지만, 이미지 품질에 따라 결과가 크게 달라질 수 있습니다.

- **이미지 품질 의존성**: 해상도가 낮거나, 글자가 흐리거나, 촬영 각도가 기울어진 이미지에서는 OCR이 텍스트를 충분히 추출하지 못할 수 있습니다.
- **문서 구조 이해 한계**: OCR은 글자 인식에 초점이 있기 때문에 표, 도장, 체크박스, 서명 위치, 조항 간 레이아웃 관계를 깊게 이해하는 데 한계가 있습니다.
- **스캔 PDF 미지원**: MVP에서는 텍스트 기반 PDF를 우선 지원하며, 이미지로만 구성된 스캔 PDF의 페이지별 OCR은 추후 확장 기능으로 분리했습니다.
- **로컬 경량 모델 한계**: 비용을 줄이기 위해 외부 유료 API 대신 로컬 경량 모델과 규칙 기반 분석을 함께 사용했습니다. 따라서 대형 상용 모델보다 표현력이나 복잡한 추론 성능은 제한될 수 있습니다.
- **법률 자문 대체 불가**: 이 기능은 계약서 검토를 돕는 보조 도구이며, 최종 계약 체결 전에는 법무 담당자나 전문가 검토가 필요합니다.

이 한계는 의도적으로 MVP 범위를 조절한 결과입니다. 먼저 텍스트 기반 계약서 분석 흐름을 안정화하고, 이후 이미지 전처리, 스캔 PDF OCR, VLM 기반 문서 이해, 조항별 근거 하이라이트 순서로 확장할 계획입니다.

### 선택지와 선택 이유

- **AI 분석 방식: 로컬 경량 NLP 엔진**
  - 선택지: 외부 AI API 사용 / 대형 로컬 모델 사용 / 계약서는 경량 추출 분석, 일반 업무는 0.5B급 로컬 생성 모델 사용
  - 선택 이유: 외부 API는 비용과 크레딧 문제가 있고, 대형 로컬 모델은 설치와 실행 부담이 큽니다. 계약서 분석은 원문 근거가 중요하므로 TextRank·TF-IDF 계열의 추출 분석을 사용하고, 미팅 준비나 컨택 문안처럼 문장 생성이 필요한 업무에는 비교적 가벼운 `Qwen/Qwen2.5-0.5B-Instruct`를 사용했습니다.

- **RAG 적용 방식: 업로드된 계약서 단위의 로컬 검색 RAG**
  - 선택지: 전체 계약서를 한 번에 분석 / 벡터 DB와 임베딩 API 사용 / 업로드 문서를 chunk로 나누고 로컬 키워드 검색으로 관련 조항 검색
  - 선택 이유: 계약서는 길고 조항별 확인이 중요하기 때문에 전체 텍스트를 한 번에 훑는 방식은 특정 조항 누락 위험이 있습니다. 반면 외부 임베딩 API나 벡터 DB는 MVP 단계에서 비용과 인프라 부담이 커질 수 있습니다. 그래서 업로드된 PDF 텍스트를 chunk로 나누고, 계약 개요·핵심 조항·의무사항·위험 요소·확인 필요 사항별 검색 질의로 관련 원문 조각을 찾는 로컬 RAG 방식을 선택했습니다.

- **계약서 입력 범위: 문서 파일과 이미지 파일 지원**
  - 선택지: PDF만 지원 / PDF와 텍스트 문서 지원 / PDF, TXT, MD, DOCX, PNG, JPG/JPEG까지 지원
  - 선택 이유: 실제 계약서는 PDF뿐 아니라 텍스트 초안, Word 문서, 캡처 이미지로도 공유될 수 있습니다. 따라서 MVP에서도 주요 문서 파일과 이미지 파일을 받아 같은 분석 파이프라인으로 처리하도록 했습니다. 다만 이미지 OCR은 품질 영향을 크게 받으므로, 스캔 PDF 전체 OCR은 추후 고도화 대상으로 분리했습니다.

- **문서 처리 방식: 긴 계약서 분할 후 분석**
  - 선택지: 계약서 전체를 한 번에 분석 / 텍스트를 분할해 분석 후 통합
  - 선택 이유: 계약서는 분량이 길고 조항이 반복되거나 세부 조건이 많아 모델 입력 한도를 넘기 쉽습니다. 분할 처리 방식은 긴 문서에서도 안정적으로 동작하고, 이후 조항별 근거 추적이나 부분 재분석으로 확장하기 쉽습니다.

- **분석 결과 형태: 자유 요약이 아닌 구조화된 출력**
  - 선택지: 자연어 요약문만 제공 / 항목별 구조화 결과 제공
  - 선택 이유: 실제 계약 검토에서는 “좋아 보이는 요약”보다 조항, 의무, 위험, 확인 사항을 빠르게 비교할 수 있는 구조가 더 중요합니다. 따라서 프론트엔드 표시와 후속 업무 연결을 고려해 고정된 출력 항목으로 정리하도록 설계했습니다.

- **리스크 표시 방식: 요약과 위험 요소를 분리**
  - 선택지: 전체 요약 안에 위험 요소를 함께 포함 / 위험 요소를 별도 섹션으로 분리
  - 선택 이유: 단순 요약은 계약 내용을 이해하는 데 필요하고, 위험 분석은 의사결정과 법무 검토에 필요합니다. 두 정보를 분리하면 사용자가 계약의 내용과 주의해야 할 문제를 혼동하지 않고 확인할 수 있습니다.

### 포트폴리오에서 강조할 수 있는 점

- 파일 업로드와 PDF/TXT/MD/DOCX/이미지 OCR 텍스트 추출을 포함한 문서 기반 AI 기능을 설계했습니다.
- 긴 문서를 chunk 단위로 분할하고, RAG로 관련 조항을 검색해 분석 근거로 반영했습니다.
- TextRank/TF-IDF 계열의 로컬 경량 분석 방식을 적용해 실제 PDF 원문 기반 분석이 가능하게 했습니다.
- 기관 리서치, 미팅 준비, 협력 평가, 1차 컨택, 후속 정리는 `Qwen/Qwen2.5-0.5B-Instruct` 로컬 모델로 생성하도록 구성했습니다.
- 계약서 원문 문장을 근거로 출력하기 때문에 면접 시연에서 실제 문서 기반 결과를 보여줄 수 있습니다.
- 단순 생성형 AI 응답이 아니라 실무자가 바로 확인할 수 있는 구조화된 결과를 목표로 했습니다.
- MVP 범위와 현재 한계를 명확히 정리해, OCR과 VLM의 차이 및 추후 확장 방향을 설명할 수 있도록 했습니다.
- 기술 선택 이유를 문서에 남겨 구현 결과뿐 아니라 판단 과정도 설명할 수 있도록 했습니다.

## 전체 대외업무 AI 기능 구성

이 프로젝트의 장기 목표는 계약서 검토 하나만 처리하는 도구가 아니라, 대외업무 흐름 전체를 지원하는 통합 에이전트입니다. 현재 단계에서는 계약서 파일 분석을 가장 깊게 구현했고, 나머지 업무 유형은 Qwen 로컬 생성 모델을 호출하도록 구성했습니다. 모델 실행에 실패하는 경우에만 입력 내용과 추가 맥락에서 핵심 키워드를 추출해 업무별 보조 결과를 생성합니다.

현재 지원하는 업무 유형은 다음과 같습니다.

- **계약 검토**: PDF, TXT, MD, DOCX, PNG, JPG/JPEG 원문을 추출하고 관련 조항을 검색해 계약 개요, 핵심 조항, 의무사항, 위험 요소, 확인 필요 사항을 생성합니다.
- **상대 기관과 참석자 사전 리서치**: AI가 리서치 목표, 확인 항목, 참석자 관점, 미팅 전 준비물을 생성합니다.
- **미팅 준비**: AI가 미팅 안건, 질문 리스트, 협상 포인트, 예상 답변 대응을 작성합니다.
- **협력 대상 평가**: AI가 전략적 적합성, 실행 가능성, 시장 영향력, 상호 이익, 리스크 기준으로 평가 프레임을 제안합니다.
- **1차 컨택 문안 작성**: AI가 개인화 포인트를 반영한 제목 후보, 이메일 본문, 후속 액션을 작성합니다.
- **미팅 후속 정리**: AI가 회의 요약, 후속 업무, 담당자, 기한, 후속 메일 초안을 생성합니다.

계약서 분석은 문서 기반 기능이므로 파일 형식별 텍스트 추출과 조항 검색까지 포함했고, 나머지 기능은 현재 입력 텍스트와 추가 맥락을 AI에 전달하는 방식으로 구현했습니다. 이후 실제 일정, CRM, 이메일, 회의록 파일 등 외부 데이터가 연결되면 각 agent의 입력 소스를 확장하는 방식으로 고도화할 수 있습니다.

## 최근 개선 기록: 로컬 AI 출력 품질 보정

일반 대외업무 기능은 비용 부담을 줄이기 위해 `Qwen/Qwen2.5-0.5B-Instruct` 로컬 경량 모델을 사용합니다. 이 선택 덕분에 외부 API 결제 없이 실행할 수 있지만, 작은 모델 특성상 일부 업무에서 출력 형식을 안정적으로 지키지 못하는 문제가 있었습니다.

### 발견한 문제

- **내부 지시문 노출**: 모델이 `사용자가 그대로 복사해 업무에 사용할 수 있게 작성하세요`, `프롬프트`, `fallback` 같은 내부 지시문을 결과에 그대로 포함하는 경우가 있었습니다.
- **Placeholder 잔존**: `1차 컨택` 결과에서 `[기관명]`, `[개인화된 1차 컨택 문안]` 같은 작성 가이드용 문구가 실제 결과처럼 남는 문제가 있었습니다.
- **빈 결과 반환**: `1차 컨택`에서 `이메일 제목`, `메일 내용` 섹션 제목만 나오고 실제 메일 본문이 비어 있는 경우가 있었습니다.
- **마크다운 렌더링 문제**: 모델이 `### 이메일 제목`, `**메일 내용**`처럼 다른 마크다운 형식을 사용하면 프론트엔드에서 결과가 어색하게 보였습니다.

### 개선 방식

- **업무별 프롬프트 강화**: `기관 리서치`, `미팅 준비`, `협력 평가`, `1차 컨택`, `후속 정리`가 각각 자기 업무 산출물만 생성하도록 출력 섹션을 명확히 제한했습니다.
- **출력 후처리 추가**: 내부 지시문, 기술 용어, placeholder, 불필요한 구분선을 제거하고 `###` 제목은 `##` 제목으로 정규화했습니다.
- **1차 컨택 재시도 로직**: AI가 `이메일 제목`과 `메일 내용`을 충분히 작성하지 못하면 메일 작성 전용 짧은 프롬프트로 한 번 더 생성하도록 했습니다.
- **Fallback 기준 강화**: 로컬 템플릿은 기본 응답이 아니라 AI 모델 실행 실패 또는 재시도 후에도 결과가 비어 있을 때만 사용하는 최후 수단으로 유지했습니다.
- **프론트엔드 렌더링 보강**: `##`, `###`, `**굵게**`, bullet, 표 형태를 화면에서 자연스럽게 렌더링하도록 처리했습니다.

### 선택 이유

대형 모델이나 외부 API로 바꾸면 출력 품질은 좋아질 수 있지만, 이 프로젝트의 현재 목표는 “무과금 로컬 실행이 가능한 포트폴리오 MVP”입니다. 따라서 모델을 바로 교체하기보다 프롬프트, 결과 검증, 후처리, 재시도 로직을 조합해 작은 모델의 약점을 보완하는 방식을 선택했습니다. 이 과정은 실제 서비스에서도 자주 필요한 LLM 응답 안정화 작업이므로, 단순 모델 호출보다 구현 판단 과정을 설명하기 좋습니다.

## 플로팅 챗봇 MVP

대외업무 기능을 탭별 실행 도구로만 제공하면 사용자가 “지금 무엇을 물어봐야 하는지”를 먼저 알아야 합니다. 이를 보완하기 위해 화면 우측 하단에 플로팅 챗봇을 추가했습니다. 챗봇은 간단한 업무 질문, 매뉴얼 검색, 담당자 확인 질문, 미팅 준비 같은 요청을 빠르게 받을 수 있는 보조 진입점입니다.

### 구현한 기능

- **우측 하단 플로팅 채팅창**: 메인 업무 화면을 유지한 상태에서 챗봇을 열고 닫을 수 있습니다.
- **텍스트 입력과 전송 이벤트**: 전송 버튼과 Enter 키로 메시지를 보낼 수 있고, Shift+Enter는 줄바꿈으로 처리합니다.
- **타이핑 애니메이션**: AI가 답변을 생성하는 동안 점 애니메이션으로 로딩 상태를 표시합니다.
- **대화 히스토리 유지**: 브라우저 `localStorage`에 최근 대화 내용을 저장하고, 백엔드 세션 ID를 함께 보관합니다.
- **퀵 버튼 Chip UI**: `매뉴얼 검색`, `담당자 찾기`, `미팅 준비`, `1차 컨택 문안` 같은 자주 쓰는 질문을 빠르게 실행할 수 있습니다.
- **채팅 세션 API**: 백엔드에서 세션 ID를 발급하고, 메모리 기반으로 최근 대화 히스토리를 관리합니다.
- **간단한 RAG 검색**: 대외업무 매뉴얼 문장을 작은 chunk로 두고, 사용자 질문과 유사한 chunk를 찾아 답변 근거로 사용합니다.
- **질문 라우팅**: 짧은 인사나 사담은 가벼운 안내로 처리하고, 업무 질문은 매뉴얼 검색과 AI 답변 생성 흐름으로 보냅니다.
- **가드레일**: API Key, 비밀번호, 내부 인증 정보 등 민감정보를 요구하는 질문은 차단하고 안전한 확인 절차를 안내합니다.
- **출처 표시**: 답변에 사용한 매뉴얼 제목을 reference로 함께 반환해, 단순 생성 답변보다 근거를 확인하기 쉽게 했습니다.

### 선택지와 선택 이유

- **히스토리 저장 방식: 브라우저 저장소 + 메모리 세션**
  - 선택지: DB 테이블 저장 / 브라우저 저장소만 사용 / 브라우저 저장소와 백엔드 메모리 세션 병행
  - 선택 이유: DB를 붙이면 사용자별 장기 기록 관리에는 유리하지만, MVP 단계에서는 마이그레이션과 운영 부담이 커집니다. 현재는 설치 부담을 줄이기 위해 브라우저 저장소로 사용성을 확보하고, 백엔드에서는 세션 ID와 최근 메시지를 메모리로 관리하도록 했습니다.

- **RAG 저장소: 외부 벡터 DB 대신 로컬 chunk 검색**
  - 선택지: Pinecone 같은 벡터 DB 사용 / 임베딩 모델 설치 / 로컬 키워드 기반 chunk 검색
  - 선택 이유: 벡터 DB와 임베딩 모델은 성능 확장에는 좋지만 별도 계정, 비용, 설치 부담이 생깁니다. 이번 단계에서는 대외업무 매뉴얼의 규모가 작다는 전제로, 로컬 chunk와 키워드 유사도 검색을 사용해 RAG 구조를 먼저 구현했습니다.

- **응답 방식: 일반 JSON 응답**
  - 선택지: 토큰 스트리밍 응답 / 일반 JSON 응답
  - 선택 이유: 스트리밍은 사용자 체감 속도를 높일 수 있지만 프론트와 백엔드 모두 이벤트 처리 구조가 추가됩니다. MVP에서는 타이핑 애니메이션으로 대기 상태를 보여주고, 안정적인 JSON 응답을 먼저 구현했습니다.

## 사용성 개선 기능

AI가 결과를 생성하는 것만으로는 실제 업무 도구처럼 느껴지기 어렵기 때문에, 결과를 확인한 뒤 바로 다음 행동으로 이어지는 기능을 추가했습니다.

- **결과 복사 버튼**: 생성된 이메일, 회의록, 계약서 분석 결과를 바로 클립보드에 복사할 수 있습니다.
- **좋아요/싫어요 피드백**: 사용자가 결과 품질을 간단히 평가할 수 있고, 백엔드 `/api/feedback` API가 메모리 기반으로 피드백을 수집합니다.
- **최근 실행 기록**: 브라우저 `localStorage`에 최근 실행 결과를 저장해 이전 결과를 다시 열어볼 수 있습니다.

이 방향을 선택한 이유는 기능 자체의 난이도보다 사용자 경험에서 느껴지는 완성도를 높이는 효과가 크기 때문입니다. 계약서 분석이나 1차 컨택 메일 생성처럼 결과물이 실제 업무 산출물인 기능은, 생성 이후 복사하거나 다시 열어보고 평가하는 흐름이 붙었을 때 “AI 데모”보다 “업무 도구”에 가깝게 보입니다.

### 선택지와 선택 이유

- **실행 기록 저장 방식: 브라우저 저장소**
  - 선택지: DB 저장 / 서버 메모리 저장 / 브라우저 `localStorage` 저장
  - 선택 이유: 최근 실행 기록은 사용자가 같은 브라우저에서 시연하거나 반복 작업할 때 체감되는 편의 기능입니다. MVP에서는 별도 DB 없이 브라우저 저장소를 사용해 설치 부담을 줄이고, 기능 흐름을 빠르게 보여줄 수 있도록 했습니다.

- **피드백 수집 방식: 메모리 기반 API**
  - 선택지: DB 테이블 저장 / 파일 저장 / 메모리 기반 API
  - 선택 이유: 좋아요/싫어요는 실제 서비스에서는 DB에 쌓아 모델 개선 데이터로 활용해야 하지만, 현재 단계에서는 “피드백 수집 흐름이 존재한다”는 것을 보여주는 것이 우선입니다. 그래서 백엔드 메모리 배열에 저장하는 가벼운 API로 구현했습니다.

- **다운로드보다 복사를 우선 구현**
  - 선택지: PDF/Markdown 다운로드 / 클립보드 복사
  - 선택 이유: 1차 컨택 메일, 미팅 후속 메일, 회의록 초안은 사용자가 바로 다른 도구에 붙여 넣는 경우가 많습니다. 따라서 파일 다운로드보다 복사 버튼이 MVP에서 더 실무적인 체감을 줍니다.

## 개발 기록 관리 방식

포트폴리오에서는 최종 결과뿐 아니라 기능을 어떤 순서로 확장했고, 왜 그런 선택을 했는지도 중요합니다. 그래서 코드 변경을 push할 때는 커밋 메시지와 [Push 기록](docs/PUSH_LOG.md)을 함께 활용합니다.

- **커밋 메시지**: 이번 변경의 핵심을 한 줄로 남겨 GitHub 히스토리에서 작업 흐름을 빠르게 파악할 수 있게 합니다.
- **Push 기록**: 기능 단위 작업 요약, 선택 이유, 검증한 내용을 문서로 남겨 면접에서 개발 과정을 설명할 수 있게 합니다.
- **README 반영**: 사용자에게 보여줄 기능 설명과 기술 선택 이유는 README에 정리해 프로젝트 첫 화면에서 바로 이해할 수 있게 합니다.

## 실행 준비

```bash
cp .env.example .env
```

`.env`에는 실행 환경과 CORS 설정만 입력합니다.

```env
LOCAL_MODEL_ID=Qwen/Qwen2.5-0.5B-Instruct
LOCAL_MODEL_MAX_NEW_TOKENS=700
APP_ENV=local
BACKEND_CORS_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

계약서 분석은 외부 API Key 없이 로컬에서 동작합니다. 기관 리서치, 미팅 준비, 협력 평가, 1차 컨택, 후속 정리는 `LOCAL_MODEL_ID`에 지정된 Hugging Face 모델을 로컬에서 로드해 생성합니다. 최초 실행 시 모델 파일이 Hugging Face 캐시에 다운로드됩니다.

## API 테스트

Health check:

```bash
curl http://127.0.0.1:8002/api/health
```

일반 업무 요청:

```bash
curl -X POST http://127.0.0.1:8002/api/agent/run \
  -H "Content-Type: application/json" \
  -d "{\"task\":\"공동 마케팅 제휴 미팅 안건을 정리해줘\",\"capability\":\"meeting_prep\"}"
```

계약서 파일 분석:

```bash
curl -X POST http://127.0.0.1:8002/api/contracts/analyze \
  -F "file=@sample-contract.pdf" \
  -F "review_focus=우리 회사 입장에서 불리한 조항을 우선 확인"
```
